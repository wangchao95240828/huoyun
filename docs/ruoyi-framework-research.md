# 若依框架调研

版本：2026-05-06

## 1. 结论

可以使用若依，但建议采用“选择性吸收”的方式，而不是整套重构为若依。

推荐方案：

1. 后端继续以现有 `apps/backend` 的 Spring Boot 3.5.x 为主。
2. 借鉴若依的系统管理能力：用户、角色、菜单、字典、参数、操作日志、代码生成。
3. 前端可以参考或引入 RuoYi-Vue3 的后台壳：登录页、侧边栏、菜单路由、权限按钮、表格页规范。
4. 主业务模块、财务账本、ACC 复刻、新智慧复刻仍然按我们自己的数据库和领域模型开发。

不建议直接整套切换为若依主架构。原因是我们已经有 PostgreSQL + RLS + 主业务库设计，且财务、订单、对账、外部系统复刻逻辑远超普通后台 CRUD。

## 3. 若依适合解决的问题

| 能力 | 对我们是否有价值 | 说明 |
| --- | --- | --- |
| 后台管理布局 | 高 | 我们当前前端还很轻，若依能快速补齐成熟后台体验 |
| 用户/角色/菜单 | 高 | 可参考其菜单权限体系，但要适配我们的 `users/roles/permissions` |
| 字典/参数 | 高 | 物流、财务、订单状态大量需要字典维护 |
| 操作日志 | 高 | 我们的权限审计、财务审计需要这类能力 |
| 代码生成 | 中 | 可加速普通主数据 CRUD，但财务和订单核心不能简单生成 |
| 定时任务 | 中 | 对账、导入、轨迹同步后续需要任务体系 |
| 数据权限 | 中 | 若依偏部门/用户数据权限，我们偏租户 + RLS，需要重写策略 |
| 微服务版 | 低 | MVP 阶段不建议上若依 Cloud，复杂度过高 |

## 4. 与当前项目的冲突点

| 维度 | 若依默认方式 | 我们当前方式 | 风险 |
| --- | --- | --- | --- |
| 数据库 | MySQL 为主 | PostgreSQL + RLS | SQL、分页、权限隔离都要适配 |
| ORM | MyBatis / MyBatis-Plus | Spring JDBC 优先 | 直接合并会改变数据访问风格 |
| 多租户 | 默认若依不是为强租户隔离设计 | 所有业务表 `tenant_id` + RLS | 不能直接复用默认数据权限 |
| 权限模型 | 菜单 + 按钮权限 | 主库 `roles/permissions` | 需要映射或改造 |
| 财务模型 | 普通后台能力 | 费用、账单、核销、复式账本 | 若依不能替代领域设计 |
| 外部系统 | 无 ACC/XQT 复刻能力 | 需要 adapter + external_* + comparison_cases | 必须自研 |

## 5. 可选方案

### 方案 A：选择性吸收若依，推荐

保留当前 Spring Boot 后端，吸收若依的后台管理思想和部分前端结构。

实施方式：

1. 前端引入 Element Plus 管理后台结构。
2. 后端补齐菜单、字典、参数、操作日志、审计日志 API。
3. 权限仍然使用我们现有 `permissions.code`，不要照搬若依表结构。
4. 普通主数据模块可参考若依代码生成思路。

优点：

- 不推翻当前 PostgreSQL/RLS/财务设计。
- 能快速提升后台体验。
- 与 Java/Spring Boot 方向一致。

缺点：

- 需要自己做一层适配，不是复制即用。

### 方案 B：整套切到 RuoYi-Vue-SpringBoot3

用若依作为新项目根基，把我们已有代码迁进去。

优点：

- 后台基础能力启动最快。
- 用户、角色、菜单、日志、代码生成现成。

缺点：

- 会重做现在的认证、权限、数据库接入。
- PostgreSQL/RLS、多租户、财务账本都要二次改造。
- ACC 和新智慧复刻仍然无法省掉。

适合条件：

- 愿意放弃当前主系统代码骨架。
- 团队更熟 MyBatis/MySQL 风格。
- MVP 范围先以后台 CRUD 为主。

### 方案 C：使用 RuoYi-Cloud

不推荐当前阶段采用。

原因：

- 3 人 3 周不适合先上微服务。
- ACC/新智慧复刻的主要风险在业务口径，不在服务拆分。
- Cloud 会带来网关、注册中心、配置中心、链路部署复杂度。

## 6. 推荐落地路径

第一周做一个小 POC，不影响主线：

| 天数 | 工作 |
| --- | --- |
| D1 | 拉取 RuoYi-Vue3 / RuoYi-Vue-SpringBoot3，跑通本地 |
| D2 | 对比若依 `sys_user/sys_role/sys_menu` 与我们 `users/roles/permissions` |
| D3 | 在当前 `apps/web` 里复刻若依式布局：侧边栏、顶部栏、菜单权限 |
| D4 | 在 `apps/backend` 增加菜单/字典/操作日志 API |
| D5 | 形成取舍清单：保留哪些若依能力，哪些不用 |

正式方案建议：

1. 不整体换框架。
2. 前端使用若依式后台体验。
3. 后端保留当前 Spring Boot 3.5.x + PostgreSQL/RLS。
4. 普通后台模块可参考若依生成器，核心业务模块手写。
5. ACC 和新智慧继续按 adapter + 主业务模型 + 对照用例方式复刻。

## 7. 决策建议

若依可以作为“后台管理加速器”，不能作为“业务系统替代品”。

对我们这个项目来说，最合适的表述是：

> 使用若依思想和前端后台壳，加速系统管理、菜单权限、字典日志、普通 CRUD；主业务、财务账本、ACC/XQT 复刻仍然坚持自研领域模型。
