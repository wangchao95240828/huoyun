## 一. 成本管理需求

### R-1 同单同渠道同类型成本 — 去重提示

**当前状态**:
- `POST /api/acc/orders/{id}/add-cost` 接口不查重, 重复添加会生成多笔
- 同一单可能误添 2 笔运费成本, 导致利润算错

**痛点**: 财务/客服重复手动加成本时没有提示, 容易误操作。

**期望**:
- 接口先做查重: `EXISTS (charges WHERE order_id=? AND charge_item_id=? AND side='AP' AND status<>'VOID')`
- 命中时返回 409: "该订单已有同类型成本 (运费 8.50 USD), 是否继续添加?"
- 前端弹"继续添加 / 覆盖原成本 / 取消" 3 按钮 modal

**验收**:
- 已有同类成本时弹窗
- 用户必须明确选"继续"才允许新加

**影响**:
- 后端: `AccOrdersController.addCost()` 加 dup check
- 前端: `doAddCost()` 处理 409, 弹 confirm modal
- DB: 无新表/新列

### R-3 添加成本时覆盖原费用

**期望**:
- modal 第 3 按钮"覆盖原成本"
- 后端: 把原 charge 标 VOID, 写入新 charge
- 反向 balance_ledger (原成本回退) + 新成本 DEBIT

**接口设计**:

```
POST /api/acc/orders/{id}/add-cost
  body: { amount, currency, chargeItemCode, overwrite: true }

  当 overwrite=true 时:
    1. 查同 charge_item_id 的现有 AP charge
    2. 若 AUDITED, 走 undoAudit (反向 ledger)
    3. 标原 charge status=VOID
    4. INSERT 新 charge (ESTIMATED PENDING)
```

### R-4 实时获取成本 (从渠道商拉)

**当前状态**: 成本完全手动填。

**期望**: UPS/FedEx/DHL 的真实账单/报价自动接入。

**分两阶段实施**:

**阶段 A (1 天) — 上传 UPS Invoice CSV 自动 match charges**:

```
财务中心 -> 应付款项 -> + 导入物流商账单 CSV
  上传 UPS Weekly Invoice
  系统按 tracking_no 自动匹配 shipments
  生成 AP charges (DRAFT 状态, 等审核)
```

**阶段 B (1 天) — 调 UPS Negotiated Rates API 实时报价**:

```
RateEngine 加 quoteFromUps() 方法
  POST https://onlinetools.ups.com/api/rating
  取 RatedShipment.NegotiatedRateCharges.TotalCharge
  落 AP charge (LIVE_QUOTE 标识)
```

### R-5 操作费 (processing_fee) 开放修改 API

**当前状态**:

- 每次出货自动收, 但前端没有编辑入口

**期望**:

- 修改后影响新单, 老单已落 charges 不变

**接口**:

```
  body: { processing_fee: 3.00, currency: "USD", ... }
```

### R-6 批量预添加渠道报价 (等真实价对比)

**业务场景**:
> 客户来 10 件货, 报价 50 美金一件。我们先按报价 50 落 AR; 等收到 UPS 真账单 (e.g. 实际 42), 系统自动对比 → 给我们 8 利润, 误差自动调账。

**期望流程**:

```
财务中心 -> 渠道商对账 -> + 新建预估批次

  渠道:        UPS-GROUND-US
  客户:        SELLER-DEMO (可选, 留空 = 通用)
  件数:        10
  单件报价:    50.00 USD
  目标重量:    1.5 kg/件
  预生效时间:  2026-07-01

系统预创建 10 条 charges (AP DRAFT, status=ESTIMATED_PRELIM)
真账单 (R-4) 拉到后自动 match + 生成差值 charge
```

**新表 cost_pre_estimates**:

```sql
CREATE TABLE cost_pre_estimates (
  id uuid PRIMARY KEY,
  channel_code text,
  customer_id uuid NULL,
  qty int,
  unit_price numeric,
  target_weight_kg numeric,
  effective_date date,
  reconciled_count int DEFAULT 0,
  status text  -- ACTIVE / EXHAUSTED / EXPIRED
);
```

### R-7 批量补收运费

**期望**:

```
制单中心 -> 批量更新计费重 (现有 tab) -> 加"批量补收"按钮
  上传 CSV: tracking_no, new_weight, new_amount

后端: 每行查原 AR freight charge
  1. amount_diff = new_amount - old_amount
  2. 若 diff > 0: INSERT 补收 charge (ESTIMATED)
  3. 若 diff < 0: INSERT 回退 charge (NEGATIVE)
  4. balance_ledger 自动 DEBIT/CREDIT
```

配合 R-8 / R-9 使用。

## 二. 应收 (AR) 管理需求

### R-8 AR 补收逻辑改 "覆盖 + 差值"

**当前状态**: 补收 = 新建一笔, 总 AR = 原 + 新 (用户看不清差额)

**期望两种语义**:

```
方式 A: 覆盖
  原 AR 13.85 -> 新 16.50
  balance_ledger:
    CREDIT 13.85 (回退原)
    DEBIT 16.50 (写新)
  净客户欠款变化: +2.65

方式 B: 补差值 (推荐)
  原 AR 13.85 保留
  INSERT 补收 charge: amount=2.65, item=ADJUST, side=AR
  balance_ledger: DEBIT 2.65
```

**接口**:

```
PATCH /api/acc/charges/{id}/restate
  body: { newAmount: 16.50, mode: "DELTA" }  // 或 "OVERWRITE"
  返: { 原amount, 新amount, deltaCharge: { id, amount } }
```

---

### R-9 应收运费列表加补收/回退列 + 余额联动

**期望**:

应收运费 tab 表头加 2 列:

| 原 charge | 补收金额 | 回退金额 | 客户当前总欠款 |
|---|---|---|---|
| 13.85 | +2.65 | 0 | 21.42 |

数据来源:
- `补收` = sum(charges WHERE source_charge_id=this AND amount > 0)
- `回退` = abs(sum(charges WHERE source_charge_id=this AND amount < 0))
- `客户当前总欠款` = financial_accounts.balance(客户预扣账户)

**DB 变更**:

```sql
ALTER TABLE charges ADD COLUMN source_charge_id uuid REFERENCES charges(id);
-- 补收/回退 charge 的源头 charge id
```

### R-11 AR/成本 行标"预估"/"实付"状态

**期望**: 列表多一列「状态来源」, 直观看出是预估还是真实

| 来源 | 显示 | 触发场景 |
|---|---|---|
| 系统自动算 (RateEngine) | 预估 | 提交订单时 |
| 手动添加 (add-cost) | 手填 | 客服点 + 添加 |
| 真账单导入 (R-4 CSV) | 真账单 | Invoice 导入 |
| 实时 API 报价 (UPS Negotiated) | 实时 | RateEngine.quoteFromUps |
| 补收差值 (R-8) | 补收 | restate 触发 |

**DB**:

```sql
ALTER TABLE charges ADD COLUMN source_type text
  CHECK (source_type IN ('ESTIMATE','MANUAL','INVOICE','LIVE_QUOTE','RESTATE'));
```

## 四. 价目表设计

### R-12 简化报价表 — 基价 × 佣金率

**当前痛点**:
- 每个客户独立配 150 阶梯 × 6 zones = 900 行 → 维护噩梦
- 客户 A 9 折, 客户 B 8.5 折, 都要手工导

**期望模型**:

```
1 份「基础价目表」 (= UPS Daily Rates 真实价)
                ↓
       × 客户的"佣金率"
                ↓
N 个客户的有效价
```

**主数据界面**:

```
主数据 -> 客户 -> 编辑 SELLER-DEMO

  价格策略:
    渠道 UPS-GROUND-US:
      基础表:    [选] UPS Daily Rates 2026 v1
      佣金率:    x 0.90  (9 折)
      底价兜底:  最低 8.00 USD

    渠道 FedEx-Ground:
      基础表:    [选] FedEx Daily Rates 2026 v1
      佣金率:    x 1.05  (加 5%)
```

**DB**:

```sql
CREATE TABLE customer_rate_strategies (
  id uuid PRIMARY KEY,
  customer_id uuid,
  channel_id uuid,
  base_rate_card_id uuid,                          -- 基础价表
  commission_rate numeric(6,4) DEFAULT 1.0000,     -- 1.00 = 原价, 0.90 = 9 折
  floor_amount numeric(10,2),                      -- 最低兜底
  effective_from timestamptz,
  effective_to timestamptz
);
```

**RateEngine 改造**:

```java
// 旧逻辑: 走客户独立 rate_card_lines
// 新逻辑: 查 customer_rate_strategies, 算 base_amount * commission_rate
```

**好处**:
- 客户改折扣 = 改一个数字
- 真实价跌价 = 改基础表 1 处, 所有客户自动跟着调
- 销售员可放心配比例

### R-2 批量导入运单

```

    customer_code, product, account, weight, country, postcode,
```

```
  返: { previewRows: [...], failedRows: [...], jobId }
```
